# Security

This describes what Phases 1 to 6 enforce and what they do not yet. The target model is spec §14.

## Owner authentication

- One owner account (`User`). `POST /auth/setup` creates it and works only while no user exists; concurrent setups are serialized by a Postgres advisory lock, so only one owner can be created.
- Passwords are hashed with argon2.
- Login creates a `UserSession` with a random 32-byte token, sent as the `office_session` cookie: `httpOnly`, `sameSite=lax`, `secure` when `NODE_ENV=production`, valid 30 days. Logout deletes the session row.
- Every HTTP route and the UI WebSocket require a valid session, except `/health`, `/auth/setup`, `/auth/login`, `GET /auth/me` (so the UI can learn that setup is required) and `/ws/worker` (which authenticates workers itself). An unauthenticated WebSocket upgrade gets HTTP 401.
- CORS allows only `WEB_ORIGIN`, with credentials.
- No secrets are sent to the browser. Worker routes never return the enrollment token hash or the credential hash.

## Worker credential

- The owner creates a worker and receives a random 32-byte enrollment token once. Only its SHA-256 hash is stored.
- On first connection the worker trades the token for a long-lived credential. The API stores only the credential's hash and clears the token hash, so the token cannot be used twice. The worker saves the credential to `$OFFICE_WORKER_HOME/credentials.json` with mode 0600.
- A worker authenticates every connection with its credential. User sessions are never accepted on the worker endpoint, and worker credentials are never accepted on user routes.
- Revoking a worker (`DELETE /workers/:id`) marks it `revoked`, closes its socket and makes its credential useless. The match on token or credential is re-checked inside the write, so a concurrent revoke wins over a connecting worker. `DELETE /workers/:id?purge=true` deletes the row instead (audit `worker.deleted`), which invalidates the credential the same way; it is refused while a run of that worker is live.
- Every `run.event` and `run.result` is checked against the run's lease: a worker can only report on runs it currently holds (see `docs/worker-protocol.md`, rejection rules).

## Workspace roots

- Each worker declares allowed workspace roots (`OFFICE_WORKSPACE_ROOTS`). The scheduler assigns a run to a worker whose roots cover the project's repository path on the same machine as the API (its `hello` `machineId` equals the API's; a worker without one is never local unless `OFFICE_TRUST_UNIDENTIFIED_WORKERS=true`), or, for mission runs, to a `canClone` worker, which works from its own clone and never receives the repository path.
- The worker checks again before running: the run's `cwd` is resolved with symlinks followed and must be an allowed root or inside one, compared by path segment (`/a/bc` is not under `/a/b`). Otherwise the run is rejected with `cwd outside allowed roots`.
- Task, inbox and chat runs without a mission run in the project repository. From Phase 4 every mission task run and the Chief's review run work in their own git worktree under `<OFFICE_WORKER_HOME>/worktrees/<runId>`, outside the repository (see "Approvals, worktrees and secrets" below). The Chief's plan run has no worktree: it runs read-only in the project repository itself.

## Skills

- **Import roots.** `POST /skills/import` with `source: local` reads a directory only if its real path (symlinks resolved) is under one of `OFFICE_SKILL_IMPORT_ROOTS` (colon-separated; default `~/.claude`); otherwise it answers `path_outside_import_roots`. Dot-directories and symlinks inside the skill directory are skipped.
- **Git import.** `source: git` accepts only `https://` URLs, plus `file://` URLs whose path is under an import root. The clone runs `git clone --depth 1` through `execFile` (no shell) with a 60 s timeout, `GIT_TERMINAL_PROMPT=0` and `GIT_ALLOW_PROTOCOL=https:file`, into a temporary directory under `OFFICE_DATA_DIR` that is removed afterwards. The optional `path` inside the clone must resolve inside the clone.
- **Review.** Imported skills start `pending_review` and cannot be pinned until the owner approves them; skills written in the UI are `approved` on creation. Every skill version is validated: `SKILL.md` with a `name` matching `^[a-z0-9][a-z0-9-]{0,63}$` and a `description`, relative paths without `..`, at most 50 files, 64 KiB per file and 512 KiB in total.
- **Untrusted text.** Skill content is treated as untrusted text: the UI renders it as text, never as HTML, and the platform never executes it. It reaches the agent only as files under the run root, which the worker validates again before writing (mode 0600) and removes after the run. A skill's instructions can still steer the agent within the agent's allowed tools; review imported skills before approving them.
- **Tool grant.** `Skill` is added to a run's allowed tools only when the agent version pins at least one skill. The subagent tool is granted only when the version defines at least one subagent, under both of its SDK names, `Agent` and `Task`: the SDK calls it `Agent` but lists it as `Task` in a session's tools, and leaving `Task` in `disallowedTools` removed it (the Phase 2 acceptance runs had no subagent tool for this reason).
- **Run roots.** Run roots live under `<OFFICE_WORKER_HOME>/runs`, outside the project repository. A starting worker deletes every directory there, so two workers must not share one `OFFICE_WORKER_HOME`, or each would sweep the other's live run roots.

## Secret redaction

- `redactSecrets` (`packages/runtime/src/redact.ts`) replaces Anthropic, GitHub, AWS and Slack key patterns, PEM private keys, and values of `*api_key*`, `*secret*`, `*token*`, `*password*` style assignments with `[REDACTED]`.
- It runs in the worker on every event before it is sent, and again in the API on every event and result before they are persisted, as a safety net against a worker that does not redact.
- Redaction is pattern-based. A secret in an unrecognized format is not caught.

## Claude permissions

- The Claude adapter runs the Agent SDK with `permissionMode: 'default'`.
- The agent version's `allowedTools`, plus the office tools of the run kind (`mcp__office__<name>`), are passed as `allowedTools`; every built-in tool not in that list is passed in `disallowedTools`. The built-in MCP resource tools (`ListMcpResourcesTool`, `ReadMcpResourceTool`, `ReadMcpResourceDirTool`) are disallowed the same way. A `canUseTool` callback is the deny path for anything else: it denies any tool that is not in the allow list.
- MCP servers: the only MCP server in a session is the in-process `office` server, and `strictMcpConfig: true` keeps out every other one (servers from the machine's Claude login, from user settings or from the project's `.mcp.json`). This replaced the Phase 2 `mcp__*` entry in `disallowedTools`, which would also have blocked the office tools. In the Phase 3 acceptance runs no `mcp__` tool other than `mcp__office__*` appeared in `agent.started`.
- Project settings (`settingSources: ['project']`) are loaded because project repositories are owner-controlled. Project allow rules and a skill's `allowed-tools` frontmatter cannot add MCP tools, because no other MCP server is loaded.
- `maxTurns` and `maxBudgetUsd` from the agent version are passed to the SDK. The budget is the SDK's soft limit on its own cost estimate (API list prices; on a subscription login it is not a bill). An agent `maxBudgetUsd` of 0 (the default) is "no agent cap" and is not passed; the lowest positive cap among the agent's, the task's and the inbox limit still applies (`minBudget` in `packages/shared`).
- The child process gets the worker's environment without `CLAUDE*` and `AI_AGENT` keys, so it uses the machine's Claude Code login or `ANTHROPIC_API_KEY`. Office's own keys are dropped too: `DATABASE_URL*`, `COOKIE_SECRET`, `REDIS_URL` and every `OFFICE_*` key.

## Office tools, messages and memory (Phase 3)

- **Project scoping.** Every office tool call is executed by the API, under the run's live lease: the worker must hold the lease and name the run's own session, or the call is answered `no_lease`. The agent and the project come from that session, never from the tool arguments. Recipients are looked up by slug among active, non-system agents; agents are not per project until `ProjectAgent` (Phase 4). Conversations, messages (`inReplyToId` included) and memory entries from another project answer `not_found`. Owner routes check a supplied `projectId` against the entry or conversation. An inbox run cannot use `awaitReply` (`not_allowed`).
- **Tool surface per run kind.** `task` runs get the version's allowed built-ins and the 13 messaging and memory tools. `inbox` runs get the same office tools, but only `Read`, `Glob` and `Grep` of the built-ins, at most 8 turns and 0.25 USD. `chat` runs (the owner's `human` conversations) keep the agent version's full tool surface and budget, like `task` runs (spec §6.3). Every run kind is gated by the project's approval policy (see "Gate order"), but a chat still works in the project repository itself, not in a worktree. `summary` runs get `submit_summary` only: no built-in tool, skill or subagent. The API checks the run kind again on every call and answers `unknown_tool` otherwise.
- **Limits.** Messages per session (`OFFICE_MSG_PER_SESSION`, default 20) and per task (`OFFICE_MSG_PER_TASK`, default 100), escalation depth (`OFFICE_ESCALATION_DEPTH`, default 2) and handoff chain length (`OFFICE_HANDOFF_CHAIN`, default 3). Counts and inserts are serialized by Postgres advisory locks, so concurrent sends cannot pass a limit. A failed check answers `limit_exceeded`. Wake runs are bounded to two per unread wake delivery, and a waiting run resumes after `OFFICE_REPLY_TIMEOUT_MINUTES` (default 60) even without a reply.
- **Untrusted text.** Message bodies and memory content are written by agents or the owner, and they reach other agents as plain prompt text: in tool results, in the resume prompt (`Reply from <sender>:` and the body) and in the context pack. They are not sanitized or marked, so a message or memory entry can steer the agent that reads it within that agent's tools. Only verified memory enters the context pack and `search_memory`. Agent proposals stay `proposed` until the owner verifies them, but the summarizer's `task_summary` is stored `verified` without an owner step. The UI renders messages and memory as text, never as HTML.
- **Tool auto-approval.** The office tools are listed in `allowedTools`, so the SDK auto-approves them like other allowed tools, and `canUseTool` is not consulted (the `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` warning names them).
- **Redaction.** Tool arguments and results are part of the event stream and pass through the same redaction as other events. Message bodies and memory content are stored as written and are not redacted.

## Approvals, worktrees and secrets (Phase 4)

- **Gate order.** Every run kind (`task` with or without a mission, `chat`, `inbox`, `plan`, `review`) carries the project's `approvalPolicy` and `approvalTimeoutMinutes`; `summary` runs carry it too but have no built-in tools. Every tool call of a run passes, in this order: (1) `disallowedTools` (built-ins the agent version does not grant are removed); (2) the `PreToolUse` hook in `packages/runtime/src/gate.ts`, which runs before any allow rule (`allowedTools`, project settings, skill frontmatter): first the read-only check, then the project's approval policy (`evaluateToolCall`: `git push` first, then `destructivePatterns` for Bash, then `sensitivePaths` by file name for `Read`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit` and `Grep` (its `path` and its `glob`, so `glob: ".env*"` asks too)); `block` denies, `ask` sends `approval.request` and waits; (3) `allowedTools`, from which `Bash`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit` are removed whenever a policy or a read-only checkout applies, so they cannot be auto-allowed; (4) `canUseTool`, which denies any tool the version does not grant and otherwise reuses the hook's decision (one decision per `toolUseId`, so the owner is asked once). `canUseTool` alone was not enough: the SDK auto-allows `allowedTools` entries before it.
- **Approval waits.** A pending approval keeps the session alive and the lease live (`waiting_approval`). It expires after `approvalTimeoutMinutes` (default 30) and the call is denied; the worker denies on its own after `approvalTimeoutMinutes + 5` minutes. The timeout is read twice: by the worker from the run spec at run start (its +5 backstop), and by the API from the project settings when the request arrives (`expiresAt`), so a settings change during a run moves only the API's expiry. `scope: task` approves later calls of the same task with the same key (Bash: the trimmed command; file tools: the path). Approvals of runs that end are expired.
- **Push, merge, deploy.** The platform never pushes, merges or deploys. A `git push` by an agent is a `git_push` approval (default `ask`). Integration is a local fast-forward of the mission branch, never of the default branch.
- **Approval policy default (2026-11-04).** A new project's policy is `auto` for every gate (`plan`, `git_push`, `merge`, `deploy`, `destructive_command`, `sensitive_path`, `budget_exceeded`), an owner decision for a single-owner local install: nothing pauses a session for the owner unless the owner tightens the policy in Settings. With `auto`, an agent's `rm -rf`, a touch of a sensitive path or a `git push` request runs without a question (push and merge are still only approval requests the platform never executes). Set the gates back to `ask` on projects with secrets or shared remotes.
- **Read-only runs.** Plan, review and analysis runs have `readOnlyCheckout`: `Edit`, `Write`, `MultiEdit` and `NotebookEdit` are denied, and so is a Bash command (whitespace-normalized) that matches a destructive pattern, contains a redirection other than a descriptor copy (`>`, `>>`, not `2>&1`), pipes into `tee`, starts a simple command with a file writer or an inline interpreter (`cp`, `mv`, `rm`, `mkdir`, `touch`, `chmod`, `chown`, `ln`, `dd`, `install`, `truncate`, `rsync`, `wget`, `curl -o`, `sed -i`, `eval`, `source`, `.`, `npm|pnpm|yarn|bun install|add|remove|update`, `pip install`, also after `sudo`, `xargs`, `env`, `nice`, `time`), or passes `--output` to git. Every `git` call in the command (also after `-C <dir>`, `--no-pager` or `--git-dir=<dir>`, after a quote as in `sh -c "git …"`, or as a path such as `/usr/bin/git` or `\git`) must be on the read-only git list, and any `git -c <k=v>` (a config override such as an alias or pager) is denied: `status`, `log`, `diff`, `show`, `blame`, `grep`, `ls-files`, `rev-parse`, `branch --list`, `worktree list`, `remote -v`, `describe`, `cat-file`; anything else (`git worktree add`, `cherry-pick`, `checkout`, …) is denied. The policy then applies as on any run, so a plan or review run's `Read` of a sensitive path asks. This Bash heuristic is defence in depth: a script file or a Bash call with no `command` still evades it; the SDK sandbox below is the real boundary.
- **Commit-equivalent git calls.** When a project's `destructivePatterns` contain `git commit`, the calls that create or rewrite commits without it (`git worktree add`, `cherry-pick`, `rebase`, `merge`, `am`, `apply`, `stash`, also after `-C <dir>`, `-c <k=v>`, `--no-pager` or `--git-dir=<dir>`) get the same `destructive_command` decision.
- **Command events.** `agent.command.executed` is emitted only after the gate allows a Bash call; a denied call appears as `agent.tool.failed` (and `agent.approval.resolved` when the owner was asked).
- **Env template versus real secrets.** The real env file (`settings.envFile`, default `.env.local`) is never copied into a worktree. The project's `envTemplate` (owner-filled dummy values) is written to that path in the worktree with mode 0600, refused when the target is a symlink, and added to `info/exclude` (git resolves it to the repository's shared `.git/info/exclude`, so the entry also applies to the main checkout) so `git add -A` cannot commit it. `checkCommand` and `setupCommand` run in the worktree through `/bin/sh -lc`, so the login shell re-sources the worker user's profile; the check's process group is killed with SIGKILL at `checkTimeoutSeconds` (a grandchild that leaves the group can survive). Check output is redacted and capped at 200 000 characters.
- **Worktree confinement (2026-11-02).** A run with a worktree (`spec.git`: code, analysis, plan and review runs) is confined two ways. The file tools (`Read`, `Glob`, `Grep`, `NotebookRead`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit`) are denied by the gate for any `file_path`, `notebook_path` or `path` that resolves outside the worktree or the run's skills dir (relative paths resolve against the worktree), so the real repository's untracked `.env.local` is out of reach. Bash runs in the Claude Agent SDK sandbox (`sandbox.enabled`, bubblewrap on Linux, `allowUnsandboxedCommands: false`): commands may write only to the worktree, the repository's `.git` dir (`spec.gitDir`, which commits need), the skills dir, the temp dir and the `~/.cache`, `~/.npm` and `~/.local/share/pnpm` caches; reads are not restricted by the sandbox, so Bash can still read files the worker user can read (`cat <repo>/.env.local`). The sandbox degrades to unsandboxed commands when its dependencies are missing (`failIfUnavailable: false`); install `bubblewrap` and `socat` on the worker host and keep `OFFICE_WORKSPACE_ROOTS` tight. Chat, inbox and non-mission task runs have no worktree and are not confined. Keep production secrets out of repositories you plan missions on, or treat the models as seeing them. Network (2026-11-04): the project setting `networkAccess` decides. `open` (the default, chosen by the owner so every project can read the web and install packages) does not sandbox Bash at all: the SDK sandbox has no allow-every-host switch and refuses `*`, so with `open` Bash on a worktree run is confined only by the file-tool gate, the read-only heuristic and the approval policy, as before 2026-11-02. `allowlist` keeps the sandbox: commands reach only `networkAllowedDomains` (`example.com`, `*.example.com`) through the SDK's proxy; any other host is denied (`deny network-outbound <host>:443 (user denied)`, curl `CONNECT tunnel failed, response 403`) because no one answers the sandbox prompt on a worker. Pick `allowlist` for repositories whose secrets must not leave the machine. In-process tools such as `WebFetch` are not gated by either mode.
- **Commit attribution.** A worktree-local `prepare-commit-msg` hook adds `Office-Agent: <agent> <runId>` to every commit made in the worktree. It sets `core.hooksPath` per worktree (which turns on `extensions.worktreeConfig` in the repository's shared config), so the project's own hooks (husky and similar) do not run for agent commits.
- **What the Chief cannot do.** The plan run gets `Read`, `Glob`, `Grep` and read-only `Bash` on a read-only worktree of the mission branch, plus `search_memory`, `read_memory`, `get_task_history`, `get_project_decisions` and `list_agents`; it cannot message, write or commit, and its plan takes effect only after the owner approves it (policy `plan`, default `ask`). The review run adds `get_task_evidence` and `review_task`, works on a read-only worktree of the mission branch, and can mark a task `done` only when the platform's evidence rule and required consultations hold (`evidence_missing` / `consultation_missing` otherwise). Only the owner overrides (`POST /tasks/:id/done|reopen|failed`), raises a mission's hard cap (`PUT /missions/:id`) or approves a `budget_exceeded` request. Plan and review runs are not subject to the budget gates.
- **Budgets.** The scheduler gates task runs on the project's daily budget (`dailyBudgetUsd`, a soft limit; a daily-budget `budget_exceeded` approval raises it for the day) and on the mission's hard cap (`Mission.budgetUsd`; reaching it raises no approval, only `PUT /missions/:id` raises it). Tasks of a mission that is not `approved`, `running` or `review` (for example `cancelled`) never start. A task run's SDK budget is the lowest positive cap among the agent version's `maxBudgetUsd` (0 = none) and the task's budget (`defaultTaskBudgetUsd` unless the plan sets one).
- **Audit log.** `AuditLog` rows (`GET /audit`) record owner and system decisions: `plan.approved`, `plan.rejected`, `plan.edited`, `plan.replan`, `approval.decided`, `approval.expired`, `budget.approved`, `mission.updated`, `mission.cancelled`, `task.reviewed` (the Chief's review or the owner), `task.override`, `task.retry`, `settings.updated`, `project_agents.updated`, `agent.updated`, `skill.approved`, `skill.rejected`, `memory.verified` and `memory.rejected`. Phase 6 adds `run.cancelled` (the owner's `POST /runs/:id/cancel`, `detail.by` the user), `worker.enrolled` (the first `hello` with an enrollment token, `detail { name, machineId }`, no user) `worker.revoked` (`DELETE /workers/:id`) and `worker.deleted` (`DELETE /workers/:id?purge=true`, `detail { name }`). The Audit page (`/audit`) lists them with filters by action, target type and time.
- **CORS.** `@fastify/cors` lists its methods explicitly (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`); the default list blocked `PUT` and `DELETE` from the browser.

## Remote workers and the git endpoint (Phase 5)

- **Bearer auth.** `/git/:projectId/*` accepts only `Authorization: Bearer <worker credential>`; the credential is matched by its hash on every request, so a revoked worker (or one whose credential is unknown) gets 401 `worker_unauthorized` at its next fetch or push, also in the middle of a session. Owner session cookies are not accepted there, and worker credentials are not accepted on owner routes.
- **Repository resolution.** The endpoint serves only the repository the database names for the project: the API links `<OFFICE_DATA_DIR>/git-roots/<projectId>/repo` to `Project.repoPath` and runs `git http-backend` with that directory as `GIT_PROJECT_ROOT`. Only the smart-HTTP paths are passed through; `..` and `.` segments answer 404. The child gets `PATH` and `HOME` only, plus the CGI and git variables, and is killed when the client disconnects.
- **The pre-receive hook.** Workers can write only fast-forwards of `refs/heads/office/*`. Any other ref, a delete, a tag or a non-fast-forward rejects the whole push, and the project's default branch is never writable, so a worker cannot change `main` or rewrite a mission branch. Nothing is pushed to the project's own `origin`.
- **Remote workers never see the control plane's filesystem.** A worker that clones receives `git.remote { path: '/git/<projectId>' }` and never `repoPath`; runs without a worktree (chat, inbox, summary, non-mission task) go only to workers whose roots cover the repository. The remote worker container mounts no host path: its credential, clones and worktrees live in the named volume `office-worker-remote` (the Phase 5 acceptance checked `docker inspect` `Mounts`). The context pack is still plain text, so it can carry a control-plane path from memory or a summary; the remote worker cannot open it.
- **Credential handling in git commands.** The worker passes the credential to git only through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0=http.extraHeader`/`GIT_CONFIG_VALUE_0` environment variables, with `GIT_TERMINAL_PROMPT=0`. It never goes into a URL, `.git/config`, a log line or an event. The credential file and the result outbox files are mode 0600.
- **What remote workers still get.** The worker credential lets a worker fetch every project's repository through the endpoint (projects are not scoped per worker), push `office/*` branches, and call the office tools for runs it holds. Revoke a worker you no longer trust. The enroll token stays in the container's environment after enrollment (it is single-use, so it no longer authenticates).
- **Network.** `API_HOST=0.0.0.0`, needed for a container or another machine to reach the API, exposes every route (including the first-run `/auth/setup`) on all interfaces. The git endpoint and `/ws/worker` are plain HTTP and WebSocket; put them behind TLS before a worker connects over an untrusted network. The host-network override `infra/compose.hostnet.yaml` shares the host's network stack with the container, so use it only where the firewall blocks the Docker bridge, and prefer a firewall rule otherwise. Postgres (5433) and Redis (6380) are published on `127.0.0.1` only (`infra/compose.yaml`); the containerised remote worker never needs them, it talks only to the API.

## Observability and hardening (Phase 6)

- **Owner run cancel.** `POST /runs/:id/cancel` is an owner route (session cookie); workers cannot call it. It sends `run.cancel` to the worker, marks the run `cancelled` and writes `run.cancelled`. A mission task run returns its task to `ready` without consuming an attempt (`?task=true` cancels the task instead); see "Phase 6 decisions" in `docs/progress.md` for plan, review and summary runs.
- **Integration needs a live lease.** The worker fast-forwards or pushes a mission branch only after the API answers `integration.check` with `ok: true`, which it does only while that worker holds the run's live lease. A residual race remains: a lease that expires between the `ok` and the push still integrates (the pre-receive hook checks only fast-forwards).
- **Result acknowledgement.** The worker deletes a result from its outbox only on `run.result.ack` or on the `No live lease` error, so a result lost with its socket is re-sent; the API applies a resend of an already final run of the same worker no second time.
- **Git endpoint time limit and protocol.** Every `git http-backend` child serving a fetch (`info/refs`, `git-upload-pack`, static objects) is killed after `OFFICE_GIT_TIMEOUT_SECONDS` (default 600). The API can answer 504 only while http-backend has not sent its headers yet; after that, a stalled fetch is cut off and the client sees a truncated response. A push (`git-receive-pack`) is exempt from the time limit, because a kill during its ref update could leave a stale ref lock; it still ends when the client disconnects. The client's `Git-Protocol` header is forwarded as `GIT_PROTOCOL`, so protocol v2 is used.
- **Machine identity override.** `OFFICE_MACHINE_ID` replaces `/etc/machine-id` on the API and on a worker. A worker with the API's id and roots covering a repository is treated as local, so set the same override only on workers that really run on the API's machine. The API does not trim the value (the worker does).
- **Observability reads records only.** The Dashboard, Live Sessions, Agent Inspector and Audit pages show status, cost and counts from stored rows (`SessionEvent`, `SubagentRun`, `UsageRecord`, `AuditLog`, `TaskRun`, `Approval`); no agent-written text sets a status chip. Command text, file paths and agent text are rendered as text.

## Unified sessions: the owner's Claude Code (2026-11-04)

- **Discovery is read-only and root-bound.** The worker lists the machine's Claude Code sessions through the Agent SDK (`listSessions`, `getSessionMessages`) and keeps only those whose `cwd` resolves (symlinks followed) under its `OFFICE_WORKSPACE_ROOTS`; a transcript, rename or delete request names a `dir` that must resolve under the roots too. Nothing is copied into the database; transcripts cross the wire reduced to text and tool names, 8000 characters per turn. Credentials, OAuth tokens and keys under `~/.claude` are never read, logged or sent.
- **Live status is observed, never guessed.** `claude agents --json --all` is the only source of "running"; without it the worker shows no status and warns once. A session a process holds is refused a second resume (`session_live`) everywhere: external terminal, Office terminal, delete. Forks are allowed because they write a new session.
- **Terminal emulators open only on this machine.** `POST /claude-sessions/:id/open` is refused `not_local` for a session on another worker; the local worker spawns `$TERMINAL` or a known emulator with argv only (`claude --resume <id>`), never a shell string, detached from the worker.
- **Office terminals (manual sessions) are the owner's own process.** `POST /terminals` and the keystrokes on `/ws/ui` need the owner's session cookie like every route; one UI socket holds a terminal's keyboard at a time (`terminal.control`), input from another socket is dropped, and a single input message is capped at 64 KB. The worker starts `claude` under a PTY in a folder under its roots with its own environment minus `OFFICE_*`, `DATABASE_URL*`, `COOKIE_SECRET` and `REDIS_URL`; no Office system prompt, skill pin or approval gate applies, and the SDK sandbox does not either: the session has exactly the permissions the owner's own `claude` has (its own settings and permission prompts). Keep other secrets out of the worker's shell. At most 8 terminals run at once; the API keeps 256 KB of scrollback each and the worker 256 KB while disconnected; SIGHUP then SIGKILL after 5 s on stop, all killed when the worker stops. Opening, stopping, background start/stop/rm, rename and delete are audited.
- **Background sessions and deletes run the CLI.** `claude --bg <prompt>`, `stop`, `rm`, `logs` are executed with argv (the prompt is one argument, 20 000 characters at most) in a folder under the roots; `claude rm` deletes the background session's worktree and `DELETE /claude-sessions/:id` deletes the transcript file, both after an in-app confirm.
- **Handoffs spend no tokens and hand over no process.** A mission draft from a transcript is built in the browser and edited by the owner before it is sent; a manual session after a mission is a fresh `claude` on the checkout.

## Conductor and Codex (2026-11-08)

- The Conductor's runs pass the SDK `tools: []`: no built-in tool at all (no Read, Bash, Edit, Workflow, ...), only its ten office tools (nine until 2026-11-10; `create_project` was added then), which read and write project records (projects, missions, verified memory) and never a project's files. Its home project holds only starter files.
- `create_project` (2026-11-10) is the one Conductor tool that touches the disk: it makes `<OFFICE_DATA_DIR>/repos/<slug>` and a repository in it. The slug is derived from the name and reduced to `a-z`, `0-9` and dashes (at most 40 characters), so a name cannot point outside that folder; a slug that a project or a folder already carries gets a number appended. Audited as `project.created_by_conductor`.
- Codex has no per-call hook. A Codex run is confined by the Codex sandbox (`workspace-write`: its working directory and the worktree's git dir; `read-only` for analysis and review tasks, verified with a real run), never asks (`approval_policy="never"`), and has network only when the project's `networkAccess` is `open` and `git_push` and `deploy` are `auto`. Projects whose `destructive_command` or `sensitive_path` policy is not `auto` refuse Codex runs, since nothing could enforce them. Codex can still read files outside the sandbox's write roots, like an unsandboxed Claude read.
- Codex's in-run budget is not enforced: usage arrives at the end of the turn and has no USD price (cost recorded as 0), so mission and daily budgets do not count Codex runs. The only hard stop is the worker's `OFFICE_CODEX_TIMEOUT_MINUTES` (default 60).

## Not yet enforced

- **Built-in tools outside the deny list**: `disallowedTools` lists `BUILTIN_TOOLS`, but the Claude Code CLI has more built-in tools (seen on 0.3.316: `Workflow`, `EnterWorktree`, `ExitWorktree`, `CronCreate`, `CronDelete`, `CronList`, `RemoteTrigger`, `ScheduleWakeup`, `SendMessage`, `SendToProject`, `SendToProjectContext`, `PushNotification`, `AskUserQuestion`, `ToolSearch`, ...). They stay available to every agent except the Conductor. Moving all agents to an allow list (`tools`) would close it.

- **Worker environment**: the agent's child process inherits the worker's whole environment apart from the keys above. Start the worker with only the variables it needs; any other secret in its environment (for example one added to `.env`, which `scripts/dev-all.sh` exports whole for convenience) reaches the agent. Use this only with throwaway local values.
- **Worktree confinement** (not built in Phase 6): `chat`, `inbox` and non-mission task runs work in the project repository itself, and no run is confined to its worktree; the approval policy gates their calls but does not sandbox them. Manual sessions (Office terminals) are by design not gated or sandboxed by Office at all.
- **Approval detection** is substring matching: `git push` and the destructive patterns are matched case-insensitively anywhere in the command (`git  push` with two spaces or `git -C x push` are missed; `echo "git push"` is caught), and sensitive paths match the file's base name only, case-sensitively.
- **Project authorization and membership**: there is one owner, who can see every project. `ProjectMember` and per-project authorization are not built (not built in Phase 6; the owner may request it).
- **Audit log**: worker heartbeats, run starts and agent tool calls are not audit rows; they are in the session events. A failed enrollment attempt is not audited.
- **Untrusted content**: tool output, agent text, skill content, messages and memory are rendered as text in the UI, never executed. Messages and memory reach other agents unmarked (see above).
