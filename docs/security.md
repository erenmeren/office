# Security

This describes what Phases 1 to 4 enforce and what they do not yet. The target model is spec §14.

## Owner authentication

- One owner account (`User`). `POST /auth/setup` creates it and works only while no user exists; concurrent setups are serialized by a Postgres advisory lock, so only one owner can be created.
- Passwords are hashed with argon2.
- Login creates a `UserSession` with a random 32-byte token, sent as the `office_session` cookie: `httpOnly`, `sameSite=lax`, `secure` when `NODE_ENV=production`, valid 30 days. Logout deletes the session row.
- Every HTTP route and the UI WebSocket require a valid session, except `/health`, `/auth/setup`, `/auth/login`, `GET /auth/me` (so the UI can learn that setup is required) and `/ws/worker` (which authenticates workers itself). An unauthenticated WebSocket upgrade gets HTTP 401.
- CORS allows only `WEB_ORIGIN`, with credentials.
- No secrets are sent to the browser. Worker routes never return the enrollment token hash or the credential hash.

## Worker credential

- The owner creates a worker and receives a random 32-byte enrollment token once. Only its SHA-256 hash is stored.
- On first connection the worker trades the token for a long-lived credential. The API stores only the credential's hash and clears the token hash, so the token cannot be used twice. The worker saves the credential to `$OFFICE_WORKER_HOME/credentials.json` with mode 0600.
- A worker authenticates every connection with its credential. User sessions are never accepted on the worker endpoint, and worker credentials are never accepted on user routes.
- Revoking a worker (`DELETE /workers/:id`) marks it `revoked`, closes its socket and makes its credential useless. The match on token or credential is re-checked inside the write, so a concurrent revoke wins over a connecting worker.
- Every `run.event` and `run.result` is checked against the run's lease: a worker can only report on runs it currently holds (see `docs/worker-protocol.md`, rejection rules).

## Workspace roots

- Each worker declares allowed workspace roots (`OFFICE_WORKSPACE_ROOTS`). The scheduler only assigns a task to a worker when the project's repository path is under one of that worker's roots.
- The worker checks again before running: the run's `cwd` is resolved with symlinks followed and must be an allowed root or inside one, compared by path segment (`/a/bc` is not under `/a/b`). Otherwise the run is rejected with `cwd outside allowed roots`.
- Task, inbox and chat runs without a mission run in the project repository. From Phase 4 every mission task run and the Chief's review run work in their own git worktree under `<OFFICE_WORKER_HOME>/worktrees/<runId>`, outside the repository (see "Approvals, worktrees and secrets" below). The Chief's plan run has no worktree: it runs read-only in the project repository itself.

## Skills

- **Import roots.** `POST /skills/import` with `source: local` reads a directory only if its real path (symlinks resolved) is under one of `OFFICE_SKILL_IMPORT_ROOTS` (colon-separated; default `<repo>/templates/skills`); otherwise it answers `path_outside_import_roots`. Dot-directories and symlinks inside the skill directory are skipped.
- **Git import.** `source: git` accepts only `https://` URLs, plus `file://` URLs whose path is under an import root. The clone runs `git clone --depth 1` through `execFile` (no shell) with a 60 s timeout, `GIT_TERMINAL_PROMPT=0` and `GIT_ALLOW_PROTOCOL=https:file`, into a temporary directory under `OFFICE_DATA_DIR` that is removed afterwards. The optional `path` inside the clone must resolve inside the clone.
- **Review.** Imported skills start `pending_review` and cannot be pinned until the owner approves them; skills written in the UI are `approved` on creation. Every skill version is validated: `SKILL.md` with a `name` matching `^[a-z0-9][a-z0-9-]{0,63}$` and a `description`, relative paths without `..`, at most 50 files, 64 KiB per file and 512 KiB in total.
- **Untrusted text.** Skill content is treated as untrusted text: the UI renders it as text, never as HTML, and the platform never executes it. It reaches the agent only as files under the run root, which the worker validates again before writing (mode 0600) and removes after the run. A skill's instructions can still steer the agent within the agent's allowed tools; review imported skills before approving them.
- **Tool grant.** `Skill` is added to a run's allowed tools only when the agent version pins at least one skill. The subagent tool is granted only when the version defines at least one subagent, under both of its SDK names, `Agent` and `Task`: the SDK calls it `Agent` but lists it as `Task` in a session's tools, and leaving `Task` in `disallowedTools` removed it (the Phase 2 acceptance runs had no subagent tool for this reason).
- **Run roots.** Run roots live under `<OFFICE_WORKER_HOME>/runs`, outside the project repository. A starting worker deletes every directory there, so two workers must not share one `OFFICE_WORKER_HOME`, or each would sweep the other's live run roots.

## Secret redaction

- `redactSecrets` (`packages/runtime/src/redact.ts`) replaces Anthropic, GitHub, AWS and Slack key patterns, PEM private keys, and values of `*api_key*`, `*secret*`, `*token*`, `*password*` style assignments with `[REDACTED]`.
- It runs in the worker on every event before it is sent, and again in the API on every event and result before they are persisted, as a safety net against a worker that does not redact.
- Redaction is pattern-based. A secret in an unrecognized format is not caught.

## Claude permissions

- The Claude adapter runs the Agent SDK with `permissionMode: 'default'`.
- The agent version's `allowedTools`, plus the office tools of the run kind (`mcp__office__<name>`), are passed as `allowedTools`; every built-in tool not in that list is passed in `disallowedTools`. The built-in MCP resource tools (`ListMcpResourcesTool`, `ReadMcpResourceTool`, `ReadMcpResourceDirTool`) are disallowed the same way. A `canUseTool` callback is the deny path for anything else: it denies any tool that is not in the allow list.
- MCP servers: the only MCP server in a session is the in-process `office` server, and `strictMcpConfig: true` keeps out every other one (servers from the machine's Claude login, from user settings or from the project's `.mcp.json`). This replaced the Phase 2 `mcp__*` entry in `disallowedTools`, which would also have blocked the office tools. In the Phase 3 acceptance runs no `mcp__` tool other than `mcp__office__*` appeared in `agent.started`.
- Project settings (`settingSources: ['project']`) are loaded because project repositories are owner-controlled. Project allow rules and a skill's `allowed-tools` frontmatter cannot add MCP tools, because no other MCP server is loaded.
- `maxTurns` and `maxBudgetUsd` from the agent version are passed to the SDK. The budget is the SDK's soft limit.
- The child process gets the worker's environment without `CLAUDE*` and `AI_AGENT` keys, so it uses the machine's Claude Code login or `ANTHROPIC_API_KEY`. Office's own keys are dropped too: `DATABASE_URL*`, `COOKIE_SECRET`, `REDIS_URL` and every `OFFICE_*` key.

## Office tools, messages and memory (Phase 3)

- **Project scoping.** Every office tool call is executed by the API, under the run's live lease: the worker must hold the lease and name the run's own session, or the call is answered `no_lease`. The agent and the project come from that session, never from the tool arguments. Recipients are looked up by slug among active, non-system agents; agents are not per project until `ProjectAgent` (Phase 4). Conversations, messages (`inReplyToId` included) and memory entries from another project answer `not_found`. Owner routes check a supplied `projectId` against the entry or conversation. An inbox run cannot use `awaitReply` (`not_allowed`).
- **Tool surface per run kind.** `task` runs get the version's allowed built-ins and the 13 messaging and memory tools. `inbox` runs get the same office tools, but only `Read`, `Glob` and `Grep` of the built-ins, at most 8 turns and 0.25 USD. `chat` runs (the owner's `human` conversations) keep the agent version's full tool surface and budget, like `task` runs (spec §6.3). Every run kind is gated by the project's approval policy (see "Gate order"), but a chat still works in the project repository itself, not in a worktree. `summary` runs get `submit_summary` only: no built-in tool, skill or subagent. The API checks the run kind again on every call and answers `unknown_tool` otherwise.
- **Limits.** Messages per session (`OFFICE_MSG_PER_SESSION`, default 20) and per task (`OFFICE_MSG_PER_TASK`, default 100), escalation depth (`OFFICE_ESCALATION_DEPTH`, default 2) and handoff chain length (`OFFICE_HANDOFF_CHAIN`, default 3). Counts and inserts are serialized by Postgres advisory locks, so concurrent sends cannot pass a limit. A failed check answers `limit_exceeded`. Wake runs are bounded to two per unread wake delivery, and a waiting run resumes after `OFFICE_REPLY_TIMEOUT_MINUTES` (default 60) even without a reply.
- **Untrusted text.** Message bodies and memory content are written by agents or the owner, and they reach other agents as plain prompt text: in tool results, in the resume prompt (`Reply from <sender>:` and the body) and in the context pack. They are not sanitized or marked, so a message or memory entry can steer the agent that reads it within that agent's tools. Only verified memory enters the context pack and `search_memory`. Agent proposals stay `proposed` until the owner verifies them, but the summarizer's `task_summary` is stored `verified` without an owner step. The UI renders messages and memory as text, never as HTML.
- **Tool auto-approval.** The office tools are listed in `allowedTools`, so the SDK auto-approves them like other allowed tools, and `canUseTool` is not consulted (the `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` warning names them).
- **Redaction.** Tool arguments and results are part of the event stream and pass through the same redaction as other events. Message bodies and memory content are stored as written and are not redacted.

## Approvals, worktrees and secrets (Phase 4)

- **Gate order.** Every run kind (`task` with or without a mission, `chat`, `inbox`, `plan`, `review`) carries the project's `approvalPolicy` and `approvalTimeoutMinutes`; `summary` runs carry it too but have no built-in tools. Every tool call of a run passes, in this order: (1) `disallowedTools` (built-ins the agent version does not grant are removed); (2) the `PreToolUse` hook in `packages/runtime/src/gate.ts`, which runs before any allow rule (`allowedTools`, project settings, skill frontmatter): first the read-only check, then the project's approval policy (`evaluateToolCall`: `git push` first, then `destructivePatterns` for Bash, then `sensitivePaths` by file name for `Read`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit`); `block` denies, `ask` sends `approval.request` and waits; (3) `allowedTools`, from which `Bash`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit` are removed whenever a policy or a read-only checkout applies, so they cannot be auto-allowed; (4) `canUseTool`, which denies any tool the version does not grant and otherwise reuses the hook's decision (one decision per `toolUseId`, so the owner is asked once). `canUseTool` alone was not enough: the SDK auto-allows `allowedTools` entries before it.
- **Approval waits.** A pending approval keeps the session alive and the lease live (`waiting_approval`). It expires after `approvalTimeoutMinutes` (default 30) and the call is denied; the worker denies on its own after `approvalTimeoutMinutes + 5` minutes. `scope: task` approves later calls of the same task with the same key (Bash: the trimmed command; file tools: the path). Approvals of runs that end are expired.
- **Push, merge, deploy.** The platform never pushes, merges or deploys. A `git push` by an agent is a `git_push` approval (default `ask`). Integration is a local fast-forward of the mission branch, never of the default branch.
- **Read-only runs.** Plan, review and analysis runs have `readOnlyCheckout`: `Edit`, `Write`, `MultiEdit` and `NotebookEdit` are denied, and so is a Bash command that matches a destructive pattern or contains ` > `, `>>` or `tee `. Every `git` call in the command (also after `-C <dir>`, `-c <k=v>` or `--no-pager`) must be on the read-only git list: `status`, `log`, `diff`, `show`, `blame`, `grep`, `ls-files`, `rev-parse`, `branch --list`, `worktree list`, `remote -v`, `describe`, `cat-file`; anything else (`git worktree add`, `cherry-pick`, `checkout`, …) is denied. The policy then applies as on any run, so a plan or review run's `Read` of a sensitive path asks. This Bash heuristic is defence in depth, not a sandbox: a determined command can still write (a script file, `sh -c`, or a Bash call with no `command`).
- **Commit-equivalent git calls.** When a project's `destructivePatterns` contain `git commit`, the calls that create or rewrite commits without it (`git worktree add`, `cherry-pick`, `rebase`, `merge`, `am`, `apply`, `stash`) get the same `destructive_command` decision.
- **Command events.** `agent.command.executed` is emitted only after the gate allows a Bash call; a denied call appears as `agent.tool.failed` (and `agent.approval.resolved` when the owner was asked).
- **Env template versus real secrets.** The real env file (`settings.envFile`, default `.env.local`) is never copied into a worktree. The project's `envTemplate` (owner-filled dummy values) is written to that path in the worktree with mode 0600, refused when the target is a symlink, and added to `info/exclude` (git resolves it to the repository's shared `.git/info/exclude`, so the entry also applies to the main checkout) so `git add -A` cannot commit it. `checkCommand` and `setupCommand` run in the worktree through `/bin/sh -lc`, so the login shell re-sources the worker user's profile; the check's process group is killed with SIGKILL at `checkTimeoutSeconds` (a grandchild that leaves the group can survive). Check output is redacted and capped at 200 000 characters.
- **Known gap: no run is confined to its worktree.** The Chief's plan run has no worktree and reads the project repository itself (its `Read` of a sensitive path now asks the owner), and no run is confined to its worktree: `Read` and Bash take absolute paths, so any agent can read files elsewhere on the worker machine that the worker user can read (the Maratus run's agents read the run root and searched `/` for a file). Keep production secrets out of repositories you plan missions on, or treat the models as seeing them.
- **Commit attribution.** A worktree-local `prepare-commit-msg` hook adds `Office-Agent: <agent> <runId>` to every commit made in the worktree. It sets `core.hooksPath` per worktree (which turns on `extensions.worktreeConfig` in the repository's shared config), so the project's own hooks (husky and similar) do not run for agent commits.
- **What the Chief cannot do.** The plan run gets `Read`, `Glob`, `Grep` and read-only `Bash`, plus `search_memory`, `read_memory`, `get_task_history`, `get_project_decisions` and `list_agents`; it cannot message, write or commit, and its plan takes effect only after the owner approves it (policy `plan`, default `ask`). The review run adds `get_task_evidence` and `review_task`, works on a read-only worktree of the mission branch, and can mark a task `done` only when the platform's evidence rule and required consultations hold (`evidence_missing` / `consultation_missing` otherwise). Only the owner overrides (`POST /tasks/:id/done|failed`), raises a mission's hard cap (`PUT /missions/:id`) or approves a `budget_exceeded` request. Plan and review runs are not subject to the budget gates.
- **Budgets.** The scheduler gates task runs on the project's daily budget (`dailyBudgetUsd`, a soft limit; a `budget_exceeded` approval raises it for the day) and on the mission's hard cap (`Mission.budgetUsd`). A task run's SDK budget is the lower of the agent version's `maxBudgetUsd` and the task's budget (`defaultTaskBudgetUsd` unless the plan sets one).
- **Audit log.** `AuditLog` rows (`GET /audit`) record owner and system decisions: `plan.approved`, `plan.rejected`, `plan.edited`, `plan.replan`, `approval.decided`, `approval.expired`, `budget.approved`, `mission.updated`, `mission.cancelled`, `task.reviewed` (the Chief's review or the owner), `task.override`, `task.retry`, `settings.updated`, `project_agents.updated`, `agent.updated`, `skill.approved`, `skill.rejected`, `memory.verified` and `memory.rejected`.
- **CORS.** `@fastify/cors` lists its methods explicitly (`GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`); the default list blocked `PUT` and `DELETE` from the browser.

## Not yet enforced

- **Worker environment**: the agent's child process inherits the worker's whole environment apart from the keys above. Start the worker with only the variables it needs; any other secret in its environment (for example one added to `.env`, which `scripts/dev-all.sh` exports whole for convenience) reaches the agent. Use this only with throwaway local values.
- **Worktree confinement** (Phase 5/6 sandbox): `chat`, `inbox` and non-mission task runs work in the project repository itself, and no run is confined to its worktree; the approval policy gates their calls but does not sandbox them.
- **Approval detection** is substring matching: `git push` and the destructive patterns are matched case-insensitively anywhere in the command (`git  push` with two spaces or `git -C x push` are missed; `echo "git push"` is caught), and sensitive paths match the file's base name only, case-sensitively.
- **Project authorization and membership** (Phase 6): there is one owner, who can see every project. `ProjectMember` and per-project authorization are not built.
- **Audit log**: worker enrollment and revocation are not audited yet, and there is no audit UI (Phase 6).
- **Untrusted content**: tool output, agent text, skill content, messages and memory are rendered as text in the UI, never executed. Messages and memory reach other agents unmarked (see above).
