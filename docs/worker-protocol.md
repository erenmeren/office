# Worker and UI protocol

Two WebSocket endpoints on the API, both carrying one JSON object per frame. Every message is validated against the Zod schemas in `packages/shared/src/protocol.ts`; a message that fails validation is answered with an `error` message.

## Worker connection: `/ws/worker`

The worker connects outbound. The endpoint is not behind the owner's cookie; the worker authenticates with its first message. The first message must be `hello`. Anything else gets `error` and the socket is closed with code 4400; an invalid or unauthenticated `hello` gets `error` and code 4401. A second connection for the same worker replaces the first, which is closed with code 4409. Revoking a worker closes its socket with code 4403.

Messages on one socket are handled strictly in order.

While the socket is down the worker keeps `run.result` (outbox), unsent `approval.request`s, a pending `integration.check` and the run's `run.event`s; `tool.call`s fail at once. Event buffer (Phase 6): until the worker has handled the next `welcome`, every `run.event` goes to an in-memory buffer per run (at most 5000; beyond that the oldest are dropped and one warning names the lost `seq` range). The worker also keeps the last 50 events it already sent per live run. On `welcome` it sends, per run and in `seq` order, those 50 plus the buffer, before re-sending any result (an applied result ends the lease, after which the API drops late events); the API stores duplicates once by `(sessionId, seq)`. A run's buffers are cleared on `run.result.ack` or the `No live lease` error. The buffer is not persisted: a worker restart still loses the events it held. An `integration.check` the executor already settled (its 30 s timer fired) is not sent after the `welcome`.

### Worker to API (`WorkerToApiSchema`)

- `hello { enrollToken? | credential?, name, capacity, allowedRoots, activeRunIds, tags, canClone, machineId? }`: authenticates the worker, either with a one-time enrollment token (first start) or with its saved credential, and reports its capacity, allowed workspace roots and the runs still executing locally (or finished with a result not delivered yet). Phase 5: `tags` (default `[]`; each `^[a-z0-9][a-z0-9-]{0,31}$`, from `OFFICE_WORKER_TAGS`) and `canClone` (default `false`, from `OFFICE_WORKER_CAN_CLONE`: the worker can clone projects from the API's git endpoint). The API stores both on the `Worker` row. Task 10b: `machineId` (1–128 characters; `/etc/machine-id` trimmed, else a random id persisted 0600 at `<OFFICE_WORKER_HOME>/machine-id`), stored as `Worker.machineId`. A worker is local only when it equals the API's own machine id; a worker that omits it is never local unless the API runs with `OFFICE_TRUST_UNIDENTIFIED_WORKERS=true`.
- `heartbeat { capacity, activeRunIds }`: sent every 10 s; updates `lastHeartbeatAt` and capacity and renews the leases of the listed runs.
- `run.accepted { runId }`: the worker has started the assigned run; the run moves `queued → running` and the task moves to `running`.
- `run.rejected { runId, reason }`: the worker refuses the run (for example `cwd outside allowed roots`, or `worker cannot clone` for a `git.remote` spec on a worker without `canClone`); the API logs it, and the run keeps its lease until it expires and the task is retried.
- `run.event { event }`: one normalized `OfficeEvent` (`type`, `seq`, `ts`, `sessionId`, `runId`, `agentId`, `projectId`, `payload`), redacted by the worker; the API redacts it again, persists it as a `SessionEvent` and publishes it to `run:<runId>` subscribers.
- `run.result { runId, sessionId, result }`: the final `RunResult` (Phase 4 adds `structuredOutput` for plan and review runs; `git { branch, baseCommit, headCommit, commits[], diffStat, filesChanged, integration: none|fast_forwarded|needs_integration, integrationReason?, worktreePath? }` (Phase 5: `integrationReason` is git's stderr from a rejected lease push, also sent as an `agent.integration.failed { reason }` event) for runs with a worktree; `check { command, status: passed|failed|timeout|skipped, exitCode, durationMs, output }` for code runs, output capped at 200 000 characters). The API stores `GitWorkspace` and `CheckResult` rows, the check output as an `Artifact`, and appends `agent.check.completed { checkResultId, command, status, exitCode, durationMs, artifactId }` to the run's events itself. The base fields are `status` (succeeded, failed, cancelled or suspended), `resultText`, `error`, `sdkSessionId` and `usage` (tokens, `costUsd`, turns and duration). The API finishes the run, the session and the task, and writes a `UsageRecord`. `suspended` (Phase 3) means the agent called an office tool with `awaitReply` and the adapter interrupted the session; `sdkSessionId` is required with it. The API then moves the run, session and task to `waiting_reply` and releases the lease instead of finishing the run.
- `tool.call { runId, sessionId, callId, name, args }` (Phase 3): the agent called office tool `name` through the in-process MCP server. The API checks that this worker holds a live lease on the run and that `sessionId` is the run's session, executes the tool with the agent and project of that session, and answers with `tool.result` carrying the same `callId`. A tool outside the run kind's set (`submit_summary` only for `summary` runs, every other tool for `task`, `inbox` and `chat` runs) is answered `unknown_tool`.
- `integration.check { runId }` (Phase 6): sent right before the worker fast-forwards the mission branch with a run's commits. The API answers `integration.allowed`.
- `approval.request { runId, sessionId, request: { requestId, toolName, input, type, reason } }` (Phase 4): the gate stopped a tool call that the project's approval policy marks `ask`. The API stores an `Approval` row (`pending`, `expiresAt` = now + `approvalTimeoutMinutes`), moves the run, session and task to `waiting_approval` (the lease stays live, the session keeps running and waits), and publishes `approval.changed`. A task-scoped approval that already matches the call, or a repeated `requestId` already decided, is answered at once with `approval.result`. A request for a run this worker holds no live lease on is answered `approval.result deny`, not `error`. Requests the worker could not send are buffered and sent after reconnect.

- `sessions.response { requestId, result? | error? }` (2026-11-04, unified sessions Phase 1): the answer to `sessions.request`. `result` is `{ kind: 'list', sessions }` (each `sessionId`, `title`, `cwd`, `gitBranch?`, `createdAt?`, `lastModified`, `fileSize?`, `live?: { pid, kind, status, name? }`), `{ kind: 'messages', entries, nextOffset }` (entries reduced to `{ uuid, role, text, tools }`, text capped at 8000 characters, `nextOffset` null once exhausted) or `{ kind: 'open', terminal }`; `error.code` is `outside_roots`, `session_live`, `no_terminal` or `internal_error`. Responses may arrive out of order with run messages.

### API to worker (`ApiToWorkerSchema`)

- `welcome { workerId, credential? }`: authentication succeeded; `credential` is present only after enrollment, and the worker saves it to `$OFFICE_WORKER_HOME/credentials.json` (mode 0600).
- `run.assign { spec }`: a leased run to execute; `RunSpec` carries run, session, agent and project ids, `cwd` (the project repository), prompt, system prompt (with the skills section appended when skills are pinned), model, effort, allowed tools, turn and budget limits, subagent limits, an optional SDK session id to resume, and:
  - `skills`: the agent version's pinned skills, each with `name`, `version`, `checksum`, `mode` (`eager` or `on_demand`) and `files` (relative path to content). The worker validates them and writes them to `<OFFICE_WORKER_HOME>/runs/<runId>/.office/.claude/skills/<name>/`, then removes the run root after the run.
  - `subagents`: the version's native subagents (`name`, `description`, `prompt`, optional `tools`, `model`, `maxTurns`, and the pinned `skills` each may use), passed to the SDK as `agents`.
  - `skillsDir`: filled in by the worker, never by the API: the `<runRoot>/.office` directory it materialized, passed to the SDK as `additionalDirectories`.
  - `kind` (Phase 3): `task`, `inbox`, `chat` or `summary` (default `task`).
  - `tools` (Phase 3): the office tool names the adapter serves for this run (from `toolsForKind`).
  - `startSeq` (Phase 3): the last `seq` already stored for the session; a resumed run numbers its events from `startSeq + 1`. It is 0 for a new run.
  - `resumeSdkSessionId`: set when a `waiting_reply` run resumes, and for a `chat` run that continues its conversation's session.
  - Phase 4 mission fields: `git { repoPath, defaultBranch, missionBranch, taskSlug, committerName, committerEmail, agentName }` (the worker creates a worktree under `<OFFICE_WORKER_HOME>/worktrees/<runId>` on the run branch `<missionBranch>-runs/<taskSlug>-<run8>` from the mission branch head, and installs the `Office-Agent:` trailer hook), `readOnlyCheckout` (plan, review and analysis runs: the gate blocks `Edit`, `Write`, `MultiEdit`, `NotebookEdit` and Bash commands that look like writes or call git outside the read-only git list, and no commit is expected), `setupCommand`, `checkCommand` and `checkTimeoutSeconds` (default 900), `env { file, vars }` (the project's dummy `envTemplate`, written to `file` in the worktree with mode 0600 and listed in the repository's shared `.git/info/exclude`), `approvalPolicy` and `approvalTimeoutMinutes` (default 30; since Task 12b set on every run kind, not only mission runs), `outputFormat { type: 'json_schema', schema }` (plan and review runs answer with structured output), and `taskKind`. Phase 5: `git` carries exactly one of `repoPath` (a worker whose `allowedRoots` cover the repository) and `remote { path: '/git/<projectId>' }` (a worker that clones; its `cwd` is the placeholder `remote`). A remote worker never receives a path of the control plane: it clones `<api>/git/<projectId>` into `<OFFICE_WORKER_HOME>/repos/<projectId>` (remote `office`), fetches `office/*` before every run, creates its worktree from that clone, and integrates by pushing the run branch and then the mission branch with `--force-with-lease=refs/heads/<mission>:<base>` after checking that the base is an ancestor of the head (see "Git endpoint" below). A mission branch that does not exist yet is created from `office/<defaultBranch>` and pushed; when the push loses to another worker's, the server's copy is adopted. Plan runs (since Task 12c) and review runs carry a `git` block with `readOnlyCheckout`: they run on a read-only worktree of the mission branch (`taskSlug` `plan` or `review`), which the worker creates from the default branch when it does not exist yet. When the worker removes a finished worktree it also deletes the run branch if the mission branch contains it (fast-forwarded or no commits); a `needs_integration` branch is kept.
- `run.cancel { runId }`: stop the run; the worker interrupts the SDK session and reports a `cancelled` result.
- `run.interrupt { runId }` (2026-11-02, owner "interrupt and send"): end the current turn; the adapter interrupts the SDK session and reports a `suspended` result with the SDK session id, exactly like `awaitReply`. The API has already stored the owner's message in the agent's human conversation and set it as the run's `waitingForMessageId`; an owner-authored waited message stands for its own reply, so the scheduler resumes the run on the same worker with the prompt `Message from the owner (your run was interrupted to deliver it):\n<body>`.
- `tool.result { callId, result }` (Phase 3): the answer to a `tool.call`. `result` is `{ ok: true, result, suspend? }` or `{ ok: false, code, error }`. Codes include `unknown_tool`, `invalid_args`, `not_found`, `limit_exceeded`, `no_lease` and `internal_error`. `suspend: true` tells the adapter to end the session after this result (the call had `awaitReply`).
- `approval.result { runId, decision: { requestId, decision: allow|deny, message? } }` (Phase 4): the owner's decision, a task-scoped match, or the timeout deny. Before sending, the API moves a run whose requests are all decided back to `running`, and records `Approval.deliveredAt` once the worker has it; undelivered decisions are re-sent on the worker's next `hello`. The worker ignores decisions for unknown or already resolved `requestId`s, and denies on its own `approvalTimeoutMinutes + 5` minutes after a request (backstop). The worker reads `approvalTimeoutMinutes` from the run spec at run start; the API reads it from the project settings when the request arrives (`expiresAt`), so a settings change during a run moves only the API's expiry.
- `run.result.ack { runId }` (Phase 6): the `run.result` was applied, or is a resend of a result already applied (see rejection rule 1). The worker deletes the result from its outbox only now.
- `integration.allowed { runId, ok, reason? }` (Phase 6): the answer to `integration.check`. `ok` is true only while this worker holds a live lease on the run (`findLeasedRun`); otherwise `ok: false, reason: 'lease lost'`. The worker's own reasons are `lease check timed out` (no answer within 30 s) and `run cancelled` (a cancel during the wait).
- `sessions.request { requestId, query }` (2026-11-04): read the worker machine's Claude Code sessions outside Office. `query.kind` is `list` (`limit`; SDK `listSessions({ includeProgrammatic: false })`, kept only when `cwd` resolves under one of the worker's `OFFICE_WORKSPACE_ROOTS`, merged with `claude agents --json` for `live`), `messages` (`sessionId`, `dir`, `offset`, `limit`; `dir` must resolve under the roots) or `open` (`sessionId`, `dir`: spawn `$TERMINAL` or the first installed emulator with `claude --resume <sessionId>` in `dir`, argv only, refused with `session_live` while the CLI still lists the session). The API sends it only to a worker whose `machineId` equals its own and waits 10 s.
- `error { message }`: the previous message was invalid or rejected (for example a `run.result` without a live lease).

### Office tool calls (Phase 3)

The worker's `ToolBridge` gives every office tool call a `callId` and sends `tool.call`. It waits at most 30 s for the `tool.result`; after that the call fails with code `timeout`. A call made while the socket is down fails at once, and calls still pending when the socket closes fail with code `disconnected`. Tool calls are not buffered across a reconnect.

After a successful call the worker records a derived event in the run's event stream:

- `send_message`, `request_help`, `handoff_task`, `escalate_to_chief` and `reply_message`: `agent.message.sent { messageId, conversationId, to?, type }`.
- `read_inbox`: `agent.message.received { count }`.
- `propose_memory`: `memory.proposed { entryId }`.

Phase 4 events: the gate emits `agent.waiting_approval { requestId, toolName, input, type, reason }` before it asks and `agent.approval.resolved { requestId, decision, message? }` after; the API emits `agent.check.completed` (above).

The adapter emits `agent.waiting_reply { messageId, to }` when a call with `awaitReply` suspends the run. The API records `agent.resumed { reason, messageId? }` itself when it resumes the run. The worker skips skill materialization for `summary` runs.

### Git endpoint (Phase 5)

`ALL /git/:projectId/<path>` on the API serves the project's repository through `git http-backend` (smart HTTP only: `info/refs`, `git-upload-pack`, `git-receive-pack`, `HEAD`, `objects/...`). The repository is the one the database names for `projectId`; the API links it as `<OFFICE_DATA_DIR>/git-roots/<projectId>/repo` and passes that directory as `GIT_PROJECT_ROOT`, so no client-supplied path reaches the filesystem.

- **Auth.** `Authorization: Bearer <worker credential>` only. A missing, unknown or revoked credential answers 401 `worker_unauthorized`; the check runs on every request, so a worker revoked mid-session fails its next fetch or push. Session cookies are not accepted here.
- **Writes.** The `pre-receive` hook (`apps/api/git-hooks/pre-receive`) accepts only fast-forwards of `refs/heads/office/*`: other refs, deletes, tags and non-fast-forwards are rejected, the project's default branch is never writable, and one bad ref rejects the whole push.
- **Client side.** The worker passes the credential through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0=http.extraHeader` environment variables with `GIT_TERMINAL_PROMPT=0`, never in a URL or a config file. A clone is made in a temporary directory and renamed into place; a broken clone is cloned again; the remote URL is set again on every sync. Integration: ancestry check, push of the run branch, then `push --force-with-lease=refs/heads/<mission>:<base>` of the mission branch; a rejected lease is `needs_integration`. When the push response is lost, `git ls-remote` decides whether it landed.
- The http-backend child is killed when the client disconnects.

### Result outbox (Phase 5, acknowledged since Phase 6)

The worker writes every `run.result` to `<OFFICE_WORKER_HOME>/outbox/<runId>.json` (mode 0600, written to a temporary file and renamed) before sending it. The entry (file and in-memory copy) is deleted only when the API answers `run.result.ack { runId }`, or `error` `No live lease for run <id> on this worker` (the run was lost and retried, so the result is dropped), or, for a stored `suspended` result only, when the API assigns the same run again (a resumed `waiting_reply` run: its previous result was applied; any other stored result is kept). Until then the run stays in `activeRunIds`, and every `welcome` re-sends every unacknowledged result, so a result whose socket died before the ack arrived is delivered again. A restarted worker loads the outbox, lists those runs in `activeRunIds` of its `hello` and re-sends the results after `welcome`. On a live socket, each `heartbeat` also re-sends every result that has gone unacknowledged for more than 30 s since it was last sent (a result lost in flight). An unreadable outbox file is skipped with a warning.

Both sides must be upgraded together (Phase 6): an API older than Phase 6 never sends `run.result.ack`, so a Phase 6 worker would keep every result in its outbox and re-send it after each reconnect (each resend then gets `error` and is finally dropped, but the outbox grows until then); an older worker ignores `run.result.ack` and `integration.allowed` and never sends `integration.check`.

### Integration lease check (Phase 6)

Before fast-forwarding the mission branch, the worker sends `integration.check { runId }` and waits up to 30 s for `integration.allowed`. If the socket is closed at that moment the check is buffered and sent after the next `welcome`, still within the same 30 s. On `ok: false` or on timeout the worker does not fast-forward: the result reports `git.integration: 'needs_integration'` with `integrationReason` `lease lost` (or the API's reason) or `lease check timed out`, the worktree is kept, and an `agent.integration.failed { reason }` event is emitted. A cancel during the wait settles it with `run cancelled`. A check that was in flight when the socket died is not re-sent; it times out. The check narrows, but does not close, the window in which a worker whose lease expires right after the answer still integrates.

### Enrollment

The owner creates a worker (`POST /workers`), which stores only the SHA-256 hash of a random enrollment token and shows the token once. The worker sends it in `hello`; the API matches a `pending` worker with that hash, generates a long-lived credential, stores its hash, clears the enrollment token hash, marks the worker `online` and returns the credential in `welcome`. Later connections send `hello` with the credential; a `revoked` worker cannot authenticate.

### Lease rules

- A run is created `queued` with a lease of 60 s (`OFFICE_LEASE_SECONDS`) on one worker.
- Each `heartbeat` (every 10 s, `OFFICE_HEARTBEAT_SECONDS`) renews the lease of every run it lists that is still `queued` or `running` on that worker, to 60 s from now.
- A disconnected worker is marked `offline`, but its runs keep their leases. The scheduler marks a run whose lease has expired as `lost`, appends a `run.lease.lost` event, and returns the task to `ready` while attempts remain (`maxAttempts`, default 2), otherwise `failed`.
- Reattach on `hello`: a reconnecting worker lists its still-executing runs in `activeRunIds`, and the API renews their leases instead of killing them. Results the worker could not send before the disconnect, including those loaded from the outbox after a restart, stay in `activeRunIds` until they are delivered.
- A lost run's session gets `run.lease.lost { workerId, retried }` (`retried`: the task went back to `ready`; otherwise it `failed`). For a `task` run, `GET /runs/:id` reports `retriedByRunId`, the next `task` run of the same task; it is `null` for every other run kind.
- Resumes are pinned (Phase 5): a `waiting_reply` run resumes only on the worker in `TaskRun.workerId`, which holds the SDK session. While that worker is offline or full the run stays parked. If the reply timeout passes while the worker is offline, the run fails with `pinned worker offline at resume` and the task is retried as a fresh run without `resumeSdkSessionId`.
- Placement (Phase 5): the scheduler picks an online worker with a free slot that can reach the repository: it is on the API's machine (same `machineId`) and its `allowedRoots` cover it (local), or, for mission runs with a `git` block (task runs of a mission, plan and review runs), it has `canClone`. Mission runs also need every tag in the project's `requiredWorkerTags`. Chat, inbox, summary and non-mission task runs go to local workers only and ignore tags. Local workers are preferred, then the one with the fewest active runs.
- The worker's free capacity is computed from the runs the database says it holds, not from the worker's own report.

### Rejection rules

1. **No live lease, no effect.** A `run.event` or `run.result` for a run that this worker does not hold with a live lease (expired, lost, reassigned after reconnect, or owned by another worker) is rejected and does not change run or task state. An event is dropped and logged; a result is answered with `error` (`No live lease for run <id> on this worker`). The lease is checked again inside the transaction that writes the result, so a lease that expires between the check and the write still loses. Exception (Phase 6): a `run.result` for a run whose `workerId` is this worker and which is already final (`succeeded`, `failed` or `cancelled`) with the same status as the result is a resend after a lost ack; it is answered with `run.result.ack` and applied no second time. Likewise a `suspended` result for a run of this worker that is `queued` again (resumed) whose session already holds the result's `sdkSessionId` is stale: it is acked and not applied. A different status, or a run this worker never owned or that was reassigned or lost, still gets the `error`. When the owner cancelled the run before its result arrived (the run is `cancelled` and the result is `cancelled`), the resend branch still records the result's usage once: a `UsageRecord` and the `costUsd` increment, guarded by `TaskRun.usageRecordedAt` (set in the same transaction; every final `completeRun` sets it too, so nothing is counted twice).
2. **Duplicate events are idempotent.** An event whose `(sessionId, seq)` is already persisted (a worker re-sending after reconnect) is stored once; the duplicate is ignored silently, not published again, and no error reaches the worker.
3. **Integration needs a live lease.** `integration.check` is answered `ok: true` only while the run's lease is live and held by this worker; the worker fast-forwards only after `ok: true`.

A `run.result` for a run still `queued` (its `run.accepted` was lost) is accepted implicitly, provided the lease is live, so a finished result is not lost.

## UI connection: `/ws/ui`

Requires the owner's session cookie; an unauthenticated upgrade gets HTTP 401. Topics are `global`, `task:<taskId>`, `run:<runId>`, `conversation:<conversationId>` (Phase 3), `mission:<missionId>` (Phase 4) and `project:<projectId>` (Phase 6). Every stored run event is published on both `run:<runId>` and `project:<projectId>`; the `project:` topic is live only (no replay, `afterSeq` is ignored) and feeds the Dashboard's live activity, which loads the stored history over HTTP (`GET /projects/:id/activity`, rows keyed `sessionId:seq`) and merges the live rows by the same key.

### UI to API (`UiClientMessageSchema`)

- `subscribe { topic, afterSeq? }`: start receiving a topic; for `run:<runId>` the API first replays persisted events with `seq > afterSeq` (default 0), then switches to live delivery.
- `unsubscribe { topic }`: stop receiving a topic.

### API to UI (`UiServerMessageSchema`)

- `event { topic, event }`: one `OfficeEvent` of a run, replayed or live (on `project:` topics live only).
- `task.status.changed { topic, task: { id, status, updatedAt } }`: a task changed status; published to `task:<id>` and `global`.
- `run.status.changed { topic, runId, status }`: a run changed status; published to `run:<id>`.
- `message.created { topic, message }` (Phase 3): a message was stored; published to `conversation:<id>` and `global`. `message` is the same view `GET /conversations/:id` returns.
- `memory.changed { topic: global, entryId, status }` (Phase 3): a memory entry was created, verified, rejected, edited or deleted.
- `approval.changed { topic, approval }` (Phase 4): an approval was created, decided or expired; published to `mission:<id>`, `run:<id>` and `global`. `approval` is the `ApprovalView` of `GET /approvals/:id`.
- `mission.status.changed { topic, mission: { id, status, updatedAt } }` (Phase 4): published to `mission:<id>` and `global`.
- `replay.done { topic, lastSeq }`: replay of a `run:` topic is complete up to `lastSeq`; everything after this is live.
- `error { message }`: invalid message, unknown run (`run not found`) or a failed replay.

Replay hands over to live delivery without gaps or duplicates: live events that arrive during replay are buffered and then passed through the same `seq` filter, so a client that reconnects with the last `seq` it saw receives every later event exactly once.
