# Phase 4 — Chief and Orchestration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner describes an outcome; the Chief plans it into a dependency graph of tasks on a read-only checkout; the owner approves the plan; the scheduler runs tasks in dependency order inside per-run git worktrees on a mission branch, with platform-side checks, approval gates for risky tool calls, budgets and retries; the Chief reviews finished work from recorded evidence and closes the mission; Mission Control shows every step with evidence links.

**Architecture:** Still the Phase 1 shape. `packages/shared` gains the plan schema (Zod and the JSON schema handed to the SDK as `outputFormat`), mission/approval/check enums, the approval policy evaluator, and the worker protocol messages for approvals and git/check results. `packages/db` gains `Mission`, `TaskDependency`, `ProjectAgent`, `Approval`, `Artifact`, `CheckResult`, `GitWorkspace`, `AuditLog`, project execution settings and the extended `Task`/`TaskRun`. `apps/api` gains missions and plan validation, plan approval, dependency-aware scheduling with budgets and concurrency, the approval lifecycle (`waiting_approval`, timeout), Chief notifications and the review session, required consultations, owner overrides. `packages/runtime` routes `canUseTool` through a policy evaluator and an approval bridge, passes `outputFormat` for plan runs and returns structured output. `apps/worker` creates worktrees on the mission branch, writes the env template, runs `checkCommand` after code runs, fast-forwards the mission branch or marks `needs_integration`, relays approval requests. `apps/web` upgrades Mission Control (plan card, dependency graph, approval card, evidence chips, budget bar) and adds Settings (execution settings, approval policies, limits, project agents).

**Tech Stack:** Unchanged: Node 26, pnpm 12, TypeScript 5.9, Fastify 5, Prisma 7, Zod 4, `@anthropic-ai/claude-agent-sdk` 0.3.x (`outputFormat: { type: 'json_schema' }`, `canUseTool`, `structured_output` on the result), Next.js 16, shadcn pattern, TanStack Query 5, vitest 5, Playwright 1.64. Git through `execFile` only. No new runtime dependency.

**Spec:** `docs/superpowers/specs/2026-10-31-agent-office-design.md` (§2 success criteria, §5.2 planes, §8 Chief/tasks/scheduling/approvals/git/checks, §9.1 Chief notifications, §10 events, §11 cancellation, §12 Mission Control is evidence-linked, §13 cost, §14 security and audit, §15 entities, §16 testing, §17 Phase 4 acceptance, §19/§20 owner decisions). Previous plans for conventions: `docs/superpowers/plans/2026-11-01-phase3-messaging-memory.md`. UI artboards: artifact "Claude Agent Office — Web UI" (`project/MissionControl.dc.html`, `project/InContext.dc.html`, `project/Dialogs.dc.html`, `project/Settings.dc.html`); the component kit is in `apps/web/src/components/ui`.

## Global Constraints

- Everything in the Phase 1–3 Global Constraints still applies (Node `>=26`, ESM, strict TS, `permissionMode: 'default'`, event envelope, redaction, no secrets to the browser, immutable `AgentVersion`, untrusted text rendered as text, project derived from the session, commit trailer `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`, English code and docs).
- Work on branch `phase4-chief-orchestration` from `main`; merge to `main` only after the final whole-branch review.
- The control plane never runs git against a project repository and never runs Claude (§5.2). Every git operation on a repository happens on the worker inside the run; the API stores what the worker reports.
- Nothing is pushed, merged or deployed by the platform in this phase. The "push branch / open PR" action in Mission Control is a request that creates an `Approval` of type `git_push` and nothing else (§8.5); executing it is left to Phase 5.
- Real secrets never enter a worktree. The worker writes the project's env template (names with dummy values set by the owner) to the configured file inside each worktree; it never copies the repository's real `.env*` files (§8.6).
- Approval gates run in the worker's `canUseTool` and in the scheduler (plan, budget). The Chief has no approval privileges; only the owner decides approvals (§8.4). Every approval decision writes an `AuditLog` row.
- A waiting approval keeps the session alive, the lease held and the worker slot occupied; after `approvalTimeoutMinutes` (default 30) the tool call is denied with an explanatory message (§8.4). Stop-and-resume for approvals is not attempted.
- `review → done` for a mission task is decided by the Chief's review run from platform-recorded evidence or by the owner's override; the evidence rules of §8.2 are enforced in the API, not by the agent's text. Tasks without a mission keep the Phase 1 behaviour (auto `done`) so Phases 1–3 flows and tests keep working.
- Retries start from the mission branch head after the last successful fast-forward, never from the mission's base commit (§20).
- `waiting_reply` and `waiting_approval` stay separate states with their own events and timeouts (§20).
- `prisma migrate dev --create-only` emits drift SQL that would drop `MemoryEntry.search` and `MemoryEntry_search_idx`; every new migration must have that SQL removed before it is applied, and `migrate deploy` is the way to confirm application (`migrate dev` hangs after applying). Document this in `docs/development.md` in Task 2.
- The Phase 4 real-Claude acceptance must not use production credentials, connect to the live Neon database, push, merge or deploy (§20). The Maratus run uses a dummy env template and `OFFICE_WORKSPACE_ROOTS` extended with `/home/meren/projects/maratus-admin`; worktrees live under `<OFFICE_WORKER_HOME>/worktrees/`, never inside the repository.
- Every task ends with its tests passing (`pnpm --filter <pkg> test`) and a commit.

## Review Focus

1. **A plan that references a cycle, an unknown agent or an agent the project does not allow.** `POST /missions` planning result with `dependsOn` forming a cycle, an unknown `agent` slug, an inactive or `isSystem` agent, or one not in `ProjectAgent` → the mission goes to `plan_failed` with the validation errors stored; no `Task` row is written. Tests in Task 4.
2. **A task whose dependency failed with no attempts left.** The dependent task becomes `blocked`, never `ready`; the mission is marked `failed` only when nothing can still run; the Chief's review run still happens. Test in Task 5.
3. **An approval decided twice, or after the timeout, or for a run that already ended.** The second decision → 409 `already_decided`; a decision after the worker already received the timeout deny → 409; a decision for an ended run → 409; the worker never receives two `approval.result` for one request. Tests in Task 6 and Task 8.
4. **A fast-forward that fails because a parallel task landed first.** The run is `succeeded` with `integrationStatus: needs_integration`, its commits stay on `office/<mission>/<task>-<run8>`, the task goes to `review` and the Chief's review marks it `reopen` or the owner integrates manually; the mission branch is untouched. Test in Task 8 and the fake e2e in Task 9.
5. **`checkCommand` that fails, hangs or prints secrets.** A non-zero exit records `CheckResult.status: failed` and the task still reaches `review` (never `done` through the Chief with a failed check for `code` tasks); a hang is killed at `checkTimeoutSeconds` (default 900) and recorded `timeout`; the output artifact is redacted before storage. Tests in Task 8.
