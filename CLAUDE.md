# Claude Agent Office

A control plane that turns Claude Code sessions into a persistent AI software team.

- Spec: `docs/superpowers/specs/2026-10-31-agent-office-design.md`
- Plan: `docs/superpowers/plans/2026-10-31-phase1-foundation.md`
- Progress: `docs/progress.md`

## Standing decisions (spec §19, §20)

- pnpm installed globally; monorepo on pnpm workspaces.
- Postgres published on host port 5433; image `pgvector/pgvector:pg16` so the extension is available later.
- Chief defaults to `opus`, specialists to `sonnet`; overridable per agent.
- Keyword search (Postgres FTS) first; vector column present but unused.
- Single-owner password login; no multi-user features beyond the `User` table.
- Interactive PTY shell deferred to Phase 6.
- Auth to Claude is the worker environment's business; adapter is credential-agnostic.
- `CLAUDE.md` at the repo root holds the standing decisions and points to `docs/progress.md`, which is updated at the end of every phase.
- Agents with no live session are woken by `question`, `help_request`, `handoff` and `escalation` messages through bounded inbox runs; senders wait for replies by suspending their run (`awaitReply`), not by blocking a worker slot (§9.1).
- `review → done` is decided by the Chief's review session from platform-recorded evidence, with owner override (§8.2).
- One mission branch, per-run worktrees fast-forwarded on success, manual integration on conflict (§8.5).
- Worker runs the project's `checkCommand` after every code run; that output is the test evidence (§8.6).
- Real `.env.local` never enters a worktree; an owner-filled dummy env template does (§8.6).
- Approval waits keep the session alive up to `approvalTimeoutMinutes`, then deny (§8.4).
- Summaries are produced by a hidden system agent on a worker, not inside the API (§9.3).
- Required consultation is a configurable acceptance criterion, set per task by the Chief's plan or the owner, never mandatory for every task. A task with `requiredConsultations: [{ agent, topic }]` cannot leave `review` as `done` until, for each entry, a `question` message from the task's agent to that agent exists in a task-linked conversation and has a reply.
- Phase 4 acceptance has two parts, both required: the deterministic fake-adapter end-to-end test, and a real Claude integration run against the Maratus repository. The real run must show (1) two independent Claude sessions communicating, (2) real code changes with independently executed tests, (3) independent QA verification, (4) evidence-based Chief review, (5) memory retrieval after all sessions are closed and restarted. It must not use production credentials, connect to the live Neon database, push, merge or deploy without explicit approval. It is not reported as passed until the execution evidence exists in the database and is reachable from Mission Control.
- Retries start from the latest safely integrated mission commit (mission branch head after the last successful fast-forward), never from the mission's original base commit.
- `waiting_reply` and `waiting_approval` are separate lifecycle states on `TaskRun` and `Task`, with their own events and timeouts. Suspended-session recovery and worker-slot release are verified by integration tests, not by inspection.
- Every success status in the UI links to the underlying session events, messages, git changes, check results or memory records.
- Pinned skills are materialized under `<OFFICE_WORKER_HOME>/runs/<runId>/.office` (passed to the SDK as an additional directory) and removed after the run.
- UI-authored skills are `approved` on creation; imported skills are `pending_review` until the owner approves them.
- `AgentSkill` and `AgentSubagent` rows belong to an `AgentVersion` and are immutable with it.
- `ProjectAgent` rows list a project's team; a project with no rows is unrestricted (every active, non-system agent).
- Skill frontmatter parsing supports single-line `key: value` only.
- Phase 3: delivery into a live session happens at session boundaries only (no streaming input yet); agents read new mail with `read_inbox` or at the next run.
- Phase 3: `question`, `help_request`, `handoff` and `escalation` wake idle agents through inbox runs with `maxTurns <= 8` and `maxBudgetUsd <= 0.25`.
- Phase 3: `awaitReply` suspends the run (`waiting_reply`, lease released); the reply resumes it with the SDK session id. `replyTimeoutMinutes` defaults to 60 (`OFFICE_REPLY_TIMEOUT_MINUTES`).
- Phase 3: `handoff_task` reassigns the task to the recipient.
- Phase 3: the office tools are an in-process SDK MCP server (`office`) fed by `tool.call`/`tool.result` over the worker socket; `strictMcpConfig: true` replaces the `mcp__*` disallow wildcard.
- Phase 3: `office-summarizer` is a hidden system agent (`isSystem`) on `haiku` that writes task summaries.
- Phase 3: memory has Postgres full-text search; the pgvector column is unused.
- Phase 3: deleting memory is a hard delete (no 30-day purge yet).
- Phase 3: inbox and chat runs have no task (`TaskRun.taskId` nullable; `agentId`/`projectId` on the run).
- Phase 4: a `Mission` (owner request) is planned by the Chief's `plan` run on a read-only worktree of the mission branch (never the real repository), which answers with the plan JSON (`PlanSchema`: `summary`, `risks`, `tasks[]` with `key`, `kind` code|analysis|review, `agent`, `dependsOn`, `requirements`, `acceptanceCriteria`, `requiredConsultations`, `approvalPoints`, `budgetUsd`). The plan is validated against the project's team, then waits for the owner (`plan` approval, policy default `ask`); approval creates the tasks and `TaskDependency` rows. `approvalPoints` live only in `Mission.plan` (no column).
- Phase 4: approval policy per project (`settings.approvalPolicy`): `plan`, `git_push`, `merge`, `deploy`, `destructive_command`, `sensitive_path`, `budget_exceeded`, each `ask`, `auto` or `block` (since 2026-11-04 a project defaults to `auto` everywhere, `AUTO_APPROVAL_POLICY`; the bare `ApprovalPolicySchema` still defaults to `ask`), plus `destructivePatterns` and `sensitivePaths`. A pending approval expires after `approvalTimeoutMinutes` (default 30) and the tool call is denied; the worker denies on its own at `approvalTimeoutMinutes + 5`.
- Phase 4: tool approvals are enforced by a `PreToolUse` hook (`packages/runtime/src/gate.ts`), and gated tools are kept out of `allowedTools` when a policy or a read-only checkout applies, because the SDK auto-allows `allowedTools` before `canUseTool`. The project's approval policy applies to every run kind (mission and non-mission task, chat, inbox, plan, review); plan and review runs keep the read-only gate on top, whose Bash check allows only the read-only git list.
- Integration (2026-11-04): before the check, a succeeded code run has its leftover changes committed by the worker (`Office auto-commit: changes <agent> left uncommitted`; `node_modules`, `dist`, `build`, `.next`, `coverage`, `out` excluded) and its run branch rebased onto the current mission head (fetched first on a clone); a clean rebase then fast-forwards as usual, a conflicting one is aborted and ends `needs_integration` with the reason. The code-task prompt tells the agent to commit and keep build output out of git.
- Phase 4: worktrees live under `<OFFICE_WORKER_HOME>/worktrees/`, never inside the repository. The mission branch is `office/<slug>-<id6>`; a run branch is `<missionBranch>-runs/<taskSlug>-<run8>` (git cannot hold both `office/<m>` and `office/<m>/<x>`). A code run's commits are fast-forwarded onto the mission branch only after a passed `checkCommand`; a failed check integrates nothing (`none`), a non-fast-forward head is `needs_integration`. Retries start from the mission branch head.
- Phase 4: a worktree-local `prepare-commit-msg` hook adds `Office-Agent: <agent> <runId>` to every agent commit. `checkCommand` runs via `/bin/sh -lc` with a process-group kill at `checkTimeoutSeconds`; its `CheckResult` is the test evidence.
- Phase 4: the project's `envTemplate` (dummy values) is written to `envFile` in the worktree, mode 0600, excluded through `info/exclude` (git resolves it to the repository's shared `.git/info/exclude`); the real env file never enters a worktree.
- Phase 4: the Chief's `review` run decides `review → done|reopen|failed` per task through `review_task`, from `get_task_evidence`: code needs at least one committed run `fast_forwarded`, no committed run after the last fast-forwarded one unintegrated, and a passed latest check; a Chief reopen counts as an attempt, so at `attempts >= maxAttempts` `review_task` refuses `reopen` and the Chief decides `done` or `failed`; analysis needs an artifact or memory entry; review needs a `review` artifact; plus the required consultations. The owner overrides with `POST /tasks/:id/done|reopen|failed`. A mission with undecided review tasks stays `review`; the owner's last decision settles it `done` or `failed`. Tasks without a mission keep Phase 1 auto-done.
- Defaults (2026-11-04, owner): `dailyBudgetUsd` 1000, `defaultMissionBudgetUsd` 5000 (a mission created without `budgetUsd` gets it as its hard cap), approval policy `auto` everywhere.
- Phase 4: budgets: `dailyBudgetUsd` is a soft per-project limit, raised by each approved daily-budget `budget_exceeded` approval that day (`dailyBudgetUsd * (1 + approved)`); `Mission.budgetUsd` is a hard cap, raised only by the owner (`PUT /missions/:id`); reaching it raises no approval. `defaultTaskBudgetUsd` caps a task run unless the plan sets `budgetUsd`.
- Phase 4: push, merge, deploy and PR creation are approval requests only; the platform never pushes. Mission cancel is atomic and idempotent and cancels live runs; tasks start only while their mission is `approved`, `running` or `review`. Greenfield: `POST /projects` without `repoPath` creates the repository at `<OFFICE_DATA_DIR>/repos/<slug>` (`git init -b <defaultBranch>` plus one empty commit, so mission branches can be created from it); an existing directory there is `409 repo_exists`. The local worker's `OFFICE_WORKSPACE_ROOTS` must cover `<OFFICE_DATA_DIR>/repos` for such projects.
- Phase 5: the API is the git endpoint for workers (`/git/<projectId>`, `git http-backend` behind the worker credential as a bearer token; revoked workers are refused per request). Only fast-forwards of `refs/heads/office/*` are accepted there (`pre-receive` hook: no other refs, deletes or tags; the default branch is never writable); nothing is pushed to the project's `origin`.
- Phase 5: remote workers (`canClone`) clone into `<OFFICE_WORKER_HOME>/repos/<projectId>` from the endpoint, never receive a control-plane path (`RunSpec.git.remote`, exactly one of `repoPath`/`remote`), and integrate by pushing the mission branch with `--force-with-lease` against the run's base after an ancestry check. Runs without a worktree (chat, inbox, summary, non-mission task) are local-only; local workers are preferred.
- Phase 5: a worker is local (gets `repoPath`, may take local-only runs) only when its `hello` `machineId` equals the API's and its `allowedRoots` cover the repository. Both compute the id the same way: `/etc/machine-id` trimmed, else a random id persisted 0600 at `<OFFICE_WORKER_HOME>/machine-id` (worker) or `<OFFICE_DATA_DIR>/machine-id` (API). A worker without `machineId` is never local unless `OFFICE_TRUST_UNIDENTIFIED_WORKERS=true` (default false). `Worker.machineId` stores it; `GET /workers` shows it.
- Phase 5: resumes are pinned to the worker that holds the SDK session (`TaskRun.workerId`); with it offline at the reply timeout the run fails and the task is retried fresh. Results are persisted in the worker outbox (`<OFFICE_WORKER_HOME>/outbox/<runId>.json`, 0600) until sent or rejected with `No live lease`.
- Phase 5: worker tags are lowercase `^[a-z0-9][a-z0-9-]{0,31}$` (`OFFICE_WORKER_TAGS`); a project's `requiredWorkerTags` must all be present on a worker for mission runs (task, plan and review runs with a worktree); local-only runs (chat, inbox, summary, non-mission task) ignore them. The remote worker container (`worker-remote`, Compose profile `remote`) mounts no host path, only the named volume `office-worker-remote`; `infra/compose.hostnet.yaml` is the opt-in host-network override for hosts whose firewall blocks the Docker bridge.
- An agent version's `maxBudgetUsd` 0 (default) means no agent cap; `minBudget` picks the lowest positive cap among agent, task and inbox limits; the adapter leaves the SDK budget unset at 0. `BUILTIN_TOOLS`/`ALWAYS_ON_TOOLS` live in `packages/shared`.
- Skills: imports (local, git, skills.sh market) are `pending_review`; `POST /skills/:id/update` re-reads a git/local source into a new version; `DELETE /skills/:id` is refused while an agent version pins the skill; the browser never calls skills.sh, the API proxies `GET /skills/market`.
- The web UI follows the Foundations artboard: tokens in `apps/web/src/app/globals.css`, every visual piece a component in `apps/web/src/components/ui` (shadcn pattern, Tailwind inside the component). Pages compose components and carry no styling of their own.
- Phase 6: observability reads records only (`SessionEvent`, `SubagentRun`, `UsageRecord`, `AuditLog`, `TaskRun`, `Approval`); no agent text drives a status chip.
- Phase 6: every stored event is also published on the UI topic `project:<projectId>`, live only (no replay).
- Phase 6: the worker outbox deletes a result only on `run.result.ack` (or the `No live lease` error); a resend of a final run of the same worker is acked idempotently; a stale `suspended` resend for a run resumed on the same worker (same `sdkSessionId`) is acked and skipped. API and worker are upgraded together.
- Phase 6: the worker sends `integration.check` before any fast-forward or push; `ok` only under a live lease; 30 s timeout; reasons `lease lost`, `lease check timed out`, `run cancelled`.
- Phase 6: owner `POST /runs/:id/cancel` marks the run `cancelled` (audit `run.cancelled`); a mission task run returns its task to `ready` without consuming an attempt (`?task=true` cancels the task); a cancelled plan run cancels the mission; a cancelled review run leaves the mission in `review`; a cancelled summary run resets `summarizedAt`. Worker enrollment and revocation are audited (`worker.enrolled`, `worker.revoked`).
- Phase 6: an old API never acks, so a Phase 6 worker against it times out every integration check and every code run with commits ends `needs_integration`.
- Phase 6: the worker buffers `run.event`s until it has handled `welcome` (per run, at most 5000, in memory only) and re-sends the last 50 sent events per live run; on `welcome` events go first, then results. An unacked result is re-sent on a heartbeat after 30 s.
- Phase 6: `TaskRun.maxBudgetUsd` is stored at creation; `SessionEvent (ts, id)` is indexed; `TaskRun.usageRecordedAt` makes an owner-cancelled run's usage count exactly once.
- Phase 6: the Dashboard activity remounts per project (`key={projectId}`) instead of resetting live rows in an effect; `/activity` rows are keyed `sessionId:seq`.
- Phase 6: `OFFICE_MACHINE_ID` overrides `/etc/machine-id` on the API and the worker; `OFFICE_GIT_TIMEOUT_SECONDS` defaults to 600; `Git-Protocol` is forwarded (v2).
- Phase 6: not built, the owner may request them: interactive PTY shell, `ProjectMember`, session Pause, messages addressed to a subagent.
- UI (2026-11-04): confirmations use the in-app `ConfirmProvider`/`useConfirm` (`components/ui/confirm-dialog.tsx`, role `alertdialog`), never `window.confirm`; Agent Studio opens the new-agent form in a `Dialog` (`/agents?new=1` opens it directly).
- Decisions page (2026-11-04): `/decisions` lists everything waiting for the owner, decidable in place: plan approvals, tool requests ("Approve all once"), review-blocked tasks (reopen/done/failed, no batch), skill imports ("Approve all"), memory proposals ("Verify all"); "Verify all" at the top takes the safe three after a confirm. The overview `attention` list (approvals, `task_decision` with `missionId`, `skill_review`, `memory_proposal`) feeds the nav badge, the Dashboard card (rows link to `/decisions`) and the Dashboard "Missions" card. Nav badges refresh on `global` hub messages (`approval.changed`, `mission.status.changed`, `task.status.changed`, `memory.changed`, `message.created`), not only on a page visit. `missionStatusLine` (`apps/web/src/lib/missions.ts`) gives every mission one sentence on what it does and whom it waits for; PlanCard and the Dashboard show it. Mission Control reads `?mission=<id>&task=<id>`.
- Blocked review decision (2026-11-04): `review_task` accepts `blocked` (Chief only, note required) when only the owner can unblock a task (network access, credentials, missing input): the task stays `review` with the note, no attempt is used, the mission stays `review` with its review run, and the owner sees it under "Needs your attention" (`attention` kind `task_decision`: tasks still in review after a finished review run) and resolves it with `POST /tasks/:id/reopen|failed`. The review prompt tells the Chief to prefer `blocked` over a reopen that would fail the same way.
- Interrupt and send (2026-11-02): `POST /runs/:id/interrupt { body }` on a `running` run stores the owner's message in the agent's human conversation, sets it as the run's `waitingForMessageId` and sends `run.interrupt` to the worker; the adapter ends the turn with a `suspended` result and the scheduler resumes the run (same worker, SDK session) with the message as the prompt. 409 `not_running` / `worker_offline`. The session page's "Interrupt and send" button uses it; plain Send is still delivered at the next run boundary.
- Worktree confinement (2026-11-02): runs with a worktree have their file tools gated to the worktree and skills dir, and Bash in the SDK sandbox (bubblewrap; writes only to the worktree, `spec.gitDir`, skills dir, temp and package caches; `failIfUnavailable: false`). Network (2026-11-04): project setting `networkAccess` `open` (default) runs Bash without the SDK sandbox, since the sandbox has no allow-every-host switch and refuses `*`; `allowlist` keeps the sandbox with `networkAllowedDomains` (`example.com` or `*.example.com`) as `sandbox.network.allowedDomains`, and an unlisted host is denied because nobody answers the sandbox prompt on a worker. The file-tool gate applies in both modes. Chat, inbox and non-mission task runs are not confined. Read-only Bash heuristic denies file writers, inline interpreters, any redirection and `git --output`; `git push` is matched after global options and whitespace normalization.
- 2026-11-02 also: `PUT /projects/:id` (name, defaultBranch), `DELETE /projects/:id` (409 `project_in_use`), project card and switcher; `POST /skills/:id/disable|enable` (a disabled skill is not materialized); a skipped check (no `checkCommand`) satisfies the code evidence rule; `review_task` from a replaced review run is refused; plan and review runs honour the mission cap and daily budget; a changed `dailyBudgetUsd` expires pending daily-budget approvals; `review → cancelled` on mission cancel; `PUT /missions/:id` refused on finished missions; `OFFICE_DATA_DIR` resolved absolute; check output redacted before capping; a half-made worktree is removed.
- Pixel Office (2026-11-02, design "Pixel Office" option 3a): `/office` draws the project's team as an isometric floor, one themed room per agent (`apps/web/src/lib/office.ts`: layout, projector, sprites; `components/office-floor.tsx`, `components/office-panel.tsx`). Rooms come from the overview `team` joined with live sessions (status, task, worker, cost, elapsed, subagents); the right column decides pending approvals and shows the selected agent's stored events, run commands and files. Each room's speech bubble is the agent's latest `agent.text` (live `project:` event, else the stored activity) or its last sent message; envelopes fly between rooms on `message.created` (`global` topic, 3.2 s) and stay while a `waiting_reply` run waits (`GET /sessions` live rows carry `waitingFor`: message id, body, recipient agent ids). Bubbles and envelopes are display only, never a status. The List and Timeline views of the design are not built.
- Project switcher (2026-11-02): the header `Select` picks the project every screen shows; the choice is kept in `localStorage` (`office.projectId`, `apps/web/src/lib/project.ts`, `useProject()`), falling back to the first project. Its last item opens the new-project form (`repoPath` optional, see greenfield).
- Unified sessions Phase 1 (2026-11-04): external Claude Code sessions are read live by the local worker (`sessions.request`/`sessions.response`, SDK `listSessions`/`getSessionMessages`, `claude agents --json` for `live`), never stored; `cwd`/`dir` must resolve under the worker's workspace roots; `open` spawns a terminal with `claude --resume <id>` as argv (`$TERMINAL` first) and is refused while the CLI still runs the session. `GET /claude-sessions` (`{ sessions, unavailable? }`, 200 even without a local worker), `GET /claude-sessions/:id/messages`, `POST /claude-sessions/:id/open`; the Live Sessions page shows them under "Claude CLI" grouped by project or unregistered folder. Phases 2 to 4 (PTY manual sessions, background agents, handoffs) are not built; see `docs/superpowers/specs/2026-11-04-unified-sessions-design.md`.
- Unified sessions Phase 2 (2026-11-04): Office-managed manual sessions are the owner's own `claude` under a PTY (`node-pty`, lazy-loaded) on the local worker: `terminal.open/input/resize/close` and `terminal.opened/output/exit/error` on the worker socket, `TerminalRegistry` in memory (no table, 256 KB scrollback, at most 8 running), `POST|GET /terminals`, `DELETE /terminals/:id`, `/ws/ui` topic `terminal:<id>` plus client `terminal.input`/`terminal.resize`; env passed through minus `OFFICE_*`, `DATABASE_URL*`, `COOKIE_SECRET`, `REDIS_URL`, no Office prompt, skills or approval gate. New sessions get `--session-id`, resumes `--resume` (refused while the CLI still runs the session). The desktop app does not rebuild `node-pty` for Electron yet.
- Unified sessions Phase 3 and gap sweep (2026-11-04): `GET /claude-sessions` fans out to every connected worker with roots (`workerId`/`workerName` on rows, remote clones joined by `/repos/<projectId>`); `POST /terminals { fork, attachId, workerId }`; one UI socket holds a terminal's keyboard (`terminal.control`); the worker buffers terminal output while disconnected; `claude agents --json --all` gives background sessions (`live.kind === 'background'`, `state`, short `id`); `sessions.request { kind: 'background', action: start|stop|rm }`, `POST /claude-sessions/background` and `/background/:id/stop|rm`; `bundle.sh` rebuilds `node-pty` for Electron.
- Unified sessions Phase 4 (2026-11-04): handoffs are owner-driven and token-free: "Start a mission from this" turns a transcript into a draft request (`apps/web/src/lib/mission-draft.ts`, `sessionStorage`) the owner edits in Mission Control; "Open a manual session here" on a finished mission opens an Office terminal with the mission's summary beside it (`/sessions?terminal=<id>&mission=<id>`). All four phases of `docs/superpowers/specs/2026-11-04-unified-sessions-design.md` are built. Manual sessions persist in `ManualSession` (loaded at API start; a running row not re-announced by its worker's first heartbeat is marked exited); Pixel Office has an owner room ("You") for manual and background sessions. Prisma queries run only when awaited: never `void prisma.x()`.
- Mission blocked reason (2026-11-04): `Scheduler.noWorkerReason(project)` and `GET /missions/:id` `blocked` explain a planning mission no worker can take (offline, repository outside every worker's roots, missing tags); the PlanCard shows "Waiting for a worker: …".
- Desktop app (2026-11-03, Linux only): `apps/desktop` (Electron) runs the bundled Postgres 17 (`@embedded-postgres/linux-x64`, 127.0.0.1:5440, scram password 0600, TCP only), `apps/desktop/server/boot.mjs` (database, migrations with Prisma's `_prisma_migrations` bookkeeping, seed, worker enroll token), the API (4100), the Next.js standalone server (3100, built with `OFFICE_DESKTOP_BUILD=1`) and the local worker as children of Electron's Node; state under `$XDG_DATA_HOME/office`, extra env from `<data>/env` (`OFFICE_WORKSPACE_ROOTS` appended). pgvector is stubbed (`apps/desktop/pgstub`, text-backed `vector` type) because the embedding column is unused; Redis is not used by any code and is not bundled. `pnpm --filter @office/desktop bundle|start|dist`.

## Commands

- `pnpm infra:up` - start Postgres (5433) and Redis (6380)
- `pnpm db:migrate` - apply Prisma migrations
- `pnpm seed` - seed the `office-sandbox` project, the 12 shipped skills, the default team and the hidden `office-summarizer` agent (idempotent)
- `scripts/dev-all.sh` - export `.env`, start infra, migrate, run `pnpm dev`
- `pnpm dev` - run all packages in watch mode
- `pnpm test` - run all tests
